> **Narrative only.** Dex is employer work, so this case study is a written account
> with no proprietary code, and figures are directional rather than exact.

## Problem

A product feature was making one model do everything — the biggest, most expensive
tier, on every request, regardless of how trivial the request was. Latency was uneven
and the bill scaled linearly with usage, which made the feature hard to justify.

## Architecture

I put a **classify-then-dispatch router** in front of three providers. Each incoming
prompt is classified, then dispatched to the cheapest model that clears that class's
eval bar; harder classes escalate to larger models, with per-provider fallback.

- **Classify** — bucket the request (extractive, structured, reasoning, creative).
- **Dispatch** — walk a cost-ordered catalog, pick the first model that clears the bar.
- **Gate** — every class has an eval contract; nothing ships that the eval doesn't pass.

## The key tradeoff

Routing is only as trustworthy as its evals. A bar set too low ships silent quality
regressions; set too high, you never realise the savings. The work was less about the
router and more about **writing honest evals** for each class — and keeping them green.

## Outcome

The traffic mix did what traffic mixes do: the large majority of requests turned out
to be extractive or short-form — exactly the classes the smallest models clear. Once
routing went in, that majority moved off the top-tier model with **no measurable
regression on the evals that gate each class**. Inference spend stopped scaling with
raw usage and started scaling with _hard_ usage, which is a much better line to be
on, and tail latency tightened as a side effect — small models aren't just cheaper,
they're faster.

Just as important: the eval suites turned "is the small model good enough?" from a
recurring debate into a diff against a dataset. Routing decisions became reviewable.
