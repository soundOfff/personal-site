A data structure is a bet about which operation has to be fast. An array bets on random access. A hash map bets on key lookup. A heap bets that the only element you ever care about is the extreme one. Pick the structure whose bet matches the question your code keeps asking, and the complexity analysis mostly does itself.

What changes between languages is not the bets — it is which ones the standard library has already placed for you. TypeScript and Python make different choices here, and the differences are exactly where interview code and production code go quietly quadratic. This post is the map I wish I'd had as one page: each structure, the question it answers in O(something good), and the one pattern per structure that does most of the work in practice.

## The map

| Structure | Core bet | Where you've already met it |
| --- | --- | --- |
| Array | O(1) access by index | Everywhere |
| Stack | O(1) at one end (LIFO) | Undo/redo, the call stack |
| Queue | O(1) at both ends (FIFO) | BFS, task scheduling |
| Linked list | O(1) insert/delete at a known node | LRU cache internals |
| Hash table | O(1) average key lookup | Every cache, every index |
| Heap | O(1) peek at min/max | OS schedulers, Dijkstra |
| Graph | model relationships, traverse in O(V+E) | Shortest-path anything |
| Union-Find | "are these connected?" in ~O(1) | Clustering, Kruskal's MST |
| BST / AVL | sorted map, O(log n) everything | Java's TreeMap, C++ std::map |
| B+ Tree | sorted map *on disk*, minimal page reads | Every `CREATE INDEX` in Postgres |
| Trie | O(L) prefix lookup | Every autocomplete box |
| Suffix array | O(m log n) substring search | Bioinformatics, plagiarism detection |
| Segment tree | O(log n) range query *with updates* | Time-series rollups |
| Bloom filter | "definitely not here" in O(1), tiny memory | RocksDB, Chrome safe-browsing |

The last four rows you will rarely implement outside a contest. The value of having them in the table is recognition: when someone asks "what was the average CPU between 2pm and 4pm?", you should hear *range query over an array* and know the answer space before opening an editor.

One row gets no section below: graphs. Not because they matter less — because traversal is a toolkit of its own, and BFS, DFS, and Dijkstra deserve more than a paragraph. That's [the follow-up post](/blog/graph-traversal-typescript-python).

## What the languages actually hand you

Here is the asymmetry that shapes everything below. **Python gives you `list`, `dict`, `set`, `heapq`, and `collections.deque`. TypeScript gives you `Array`, `Map`, and `Set` — and that's it.** TypeScript has no heap, no deque, no sorted map; neither language has a linked list, trie, union-find, or segment tree. Both languages also hide static arrays from you entirely: every `list` and every `Array` is dynamic, resizing when capacity is hit, which costs you nothing you'll notice and buys you never thinking about capacity again.

Two practical consequences:

**The queue trap.** A queue needs O(1) at both ends. Python's `list.pop(0)` and TypeScript's `Array.shift()` are both O(n) — every remaining element shifts left. Python has the fix built in:

```python
from collections import deque

queue = deque([start])
node = queue.popleft()   # O(1)
```

TypeScript does not. For interview-sized inputs, `shift()` is fine and everyone knows it; for production, you either keep a read-index into a plain array or bring a dependency. The point is to know you are making that trade, not to discover it in a profiler.

**The heap gap.** Python's `heapq` is right there — min-heap only, so a max-heap is "negate on the way in, negate on the way out", which is ugly and universal. TypeScript has nothing, and this is the single most common "wait, really?" for people arriving from Python or Java. In an interview you say so out loud and write the simplest thing that preserves the interface:

```ts
class MinHeap {
  private heap: number[] = [];
  push(val: number): void {
    this.heap.push(val);
    this.heap.sort((a, b) => a - b); // O(n log n) per push — say it, then move on
  }
  pop(): number | undefined { return this.heap.shift(); }
  peek(): number | undefined { return this.heap[0]; }
}
```

That is not a heap; it is a sorted array wearing a heap's interface. Naming the gap and bounding the cost is worth more than reproducing sift-up from memory under a clock.

## Arrays, and the one pattern that pays rent

For everything beyond the basics, the leverage is not in the structure — it is in one pattern per structure that converts an O(n²) instinct into an O(n) solution. For arrays, that pattern is the **prefix sum**: spend O(n) once to build an accumulator, then answer any range-sum question in O(1).

```python
def build_prefix(nums: list[int]) -> list[int]:
    prefix = [0] * (len(nums) + 1)
    for i, n in enumerate(nums):
        prefix[i + 1] = prefix[i] + n
    return prefix

def range_sum(prefix: list[int], l: int, r: int) -> int:
    return prefix[r + 1] - prefix[l]   # sum of [l, r] inclusive, O(1)
```

```ts
function buildPrefix(nums: number[]): number[] {
  const prefix = new Array(nums.length + 1).fill(0);
  for (let i = 0; i < nums.length; i++) prefix[i + 1] = prefix[i] + nums[i];
  return prefix;
}

function rangeSum(prefix: number[], l: number, r: number): number {
  return prefix[r + 1] - prefix[l];
}
```

The off-by-one is load-bearing: the extra leading zero is what lets `range_sum(prefix, 0, r)` work without a special case. Prefix sums are the *static* answer to range queries; the moment the underlying array needs updates between queries, you have walked into segment-tree territory — same question, harder bet.

## Stacks: the monotonic trick

A stack is a dynamic array you only touch at one end — both languages do it natively with `push`/`pop` (or `append`/`pop`), no ceremony. The pattern worth drilling is the **monotonic stack**: for each element, find the next greater (or smaller) element to its right, in O(n) instead of the naive O(n²).

```ts
function nextGreater(nums: number[]): number[] {
  const result = new Array(nums.length).fill(-1);
  const stack: number[] = []; // indices of elements still waiting for their answer

  for (let i = 0; i < nums.length; i++) {
    while (stack.length && nums[i] > nums[stack[stack.length - 1]]) {
      result[stack.pop()!] = nums[i];
    }
    stack.push(i);
  }
  return result;
}
// [2,1,2,4,3] → [4,2,4,-1,-1]
```

The invariant — the stack always holds indices of a non-increasing run — is what makes the amortized analysis one sentence: every index is pushed once and popped at most once, so the nested-looking loop is O(n). Stock-span, daily-temperatures, largest-rectangle-in-histogram are all this one trick in costume.

## Hash maps: store the complement, not the search

Both languages make the hash map their best structure — Python's `dict` and TypeScript's `Map` are O(1) average for get/set/delete, and most "make it faster" interview answers are some form of "put a hash map in front of it." The canonical pattern is two-sum: instead of scanning for a partner for each element (O(n²)), record what you've *seen* and ask whether the current element completes a pair:

```python
def two_sum(nums: list[int], target: int) -> list[int]:
    seen: dict[int, int] = {}          # value -> index
    for i, n in enumerate(nums):
        if target - n in seen:
            return [seen[target - n], i]
        seen[n] = i
    return []
```

The generalizable move is the reframe: *don't search forward for what you need; remember backward what you've had.* Frequency counts, anagram grouping, and memoization are the same move with different keys.

## The ones you always build from scratch

Linked lists, tries, and union-find exist in neither standard library, and that turns out to be fine — each is under twenty lines, and the lines are the same every time. Union-find is the one I'd actually memorize, because it answers a question nothing else answers cheaply: *are these two things in the same group?* — in O(α(n)) per query. α is the inverse Ackermann function, and α(n) ≤ 4 for any n that fits in hardware, so treat it as constant.

```python
class UnionFind:
    def __init__(self, n: int):
        self.parent = list(range(n))
        self.rank = [0] * n

    def find(self, x: int) -> int:
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])  # path compression
        return self.parent[x]

    def union(self, x: int, y: int) -> bool:
        px, py = self.find(x), self.find(y)
        if px == py:
            return False
        if self.rank[px] < self.rank[py]:
            px, py = py, px
        self.parent[py] = px                            # union by rank
        if self.rank[px] == self.rank[py]:
            self.rank[px] += 1
        return True
```

Both optimizations matter and neither is optional: path compression flattens the tree as you query it, union by rank keeps it from growing tall in the first place. Connected components, cycle detection in undirected graphs, Kruskal's MST, "do these accounts belong to the same person" — all union-find, all the same twenty lines.

Linked lists earn their twenty lines differently: not as a container you'd reach for (O(n) to *find* anything), but as the only structure with O(1) delete at a known node — which is why the textbook LRU cache is a hash map pointing into a doubly linked list, and why the fast-and-slow-pointer trick (cycle detection, find-the-middle in one pass) keeps showing up.

The LRU cache is worth thirty extra seconds, because it is the one interview classic that *composes* two structures: the hash map answers "do we have this key?" in O(1), the linked list answers "which entry is oldest?" in O(1), and every node is reachable from both. And here is where knowing your standard library's bets pays off twice — JavaScript's `Map` iterates in insertion order, which is a linked list already threaded through the buckets for you. A full LRU in TypeScript is a dozen lines and no node class:

```ts
class LRUCache<K, V> {
  private map = new Map<K, V>();
  constructor(private capacity: number) {}

  get(key: K): V | undefined {
    if (!this.map.has(key)) return undefined;
    const val = this.map.get(key)!;
    this.map.delete(key);
    this.map.set(key, val);   // re-insert → now the newest entry
    return val;
  }

  put(key: K, val: V): void {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, val);
    if (this.map.size > this.capacity) {
      this.map.delete(this.map.keys().next().value!);   // first key = oldest
    }
  }
}
```

Python plays the same trick with `collections.OrderedDict` — `move_to_end` on access, `popitem(last=False)` to evict — and if the cache fronts a pure function, `functools.lru_cache` is one decorator. The hand-rolled doubly-linked-list version is still worth understanding, because it is exactly what these implementations do underneath. But reaching for it first is solving a problem your standard library already solved.

## The ones you only reason about

B-Trees and Bloom filters close the table, and the honest advice is: understand them, never implement them. A B+ Tree node is sized to one disk page, so hundreds of keys per node means a million-row index is three or four levels deep — three or four disk reads for any lookup. That sentence is the entire reason `CREATE INDEX` makes your query fast, and it is worth more in a system-design conversation than any implementation would be. A Bloom filter is the inverse trade: a few kilobits buy you "this key *definitely* doesn't exist", which is how RocksDB and Cassandra skip disk reads for absent keys — false positives possible, false negatives never.

The pattern across this whole post is the same one: the structure is rarely the hard part. The hard part is hearing the question your code keeps asking — *next greater? same group? range with updates? definitely absent?* — and recognizing which bet, already placed and paid for, answers it. That recognition reflex is the part of contest training that actually transfers, which is [its own post](/blog/what-icpc-trains-you-to-see). The table is the artifact. The rest is recognition.
