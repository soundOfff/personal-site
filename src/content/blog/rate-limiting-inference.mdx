The [portfolio agent](/#playground) accepts questions from anonymous visitors and makes model calls billed to my account. Before exposing that endpoint, I need to decide what stops a script from turning the demo into an ongoing expense.

A request limit helps, but a request limit and a spending guarantee are different contracts. This article describes the controls in the current implementation, including where their guarantees stop.

> Updated October 2026. The original router demo has been replaced by an A2UI agent. The old article's five-per-minute limit and per-request cost examples no longer described the endpoint. The current controls are documented below.

## Start with the request path

The browser sends a question to `/api/a2ui`. The endpoint checks that the agent is configured, validates the question, consumes the rate-limit budgets, and only then calls the model.

The request boundary accepts a message of at most 400 characters and trims client-supplied history. The agent includes its own instructions and retrieved portfolio context as well, so 400 characters is not a bound on the full input token count.

The agent defaults to `anthropic/claude-haiku-4.5`, allows a model override through configuration, and requests at most 2,048 output tokens. Those settings constrain a call. They do not establish a permanent dollar ceiling independent of model choice, input context, or provider pricing.

## Three windows, checked in order

The controls in `src/lib/ratelimit.ts` are:

| Window              | Configured allowance | Purpose                                   |
| ------------------- | -------------------- | ----------------------------------------- |
| Per IP, per minute  | 3 turns              | Slow repeated submissions.                |
| Per IP, per UTC day | 5 turns              | Give each visitor a small allowance.      |
| Shared, per UTC day | 300 turns            | Target an aggregate daily request budget. |

These are configured allowances, not exact distributed admission guarantees. The endpoint checks burst, visitor, and shared budgets in that order. A request rejected by the first check does not consume the later ones.

The per-IP controls return HTTP 429 with a `Retry-After` header. If the shared counter reports exhaustion, the endpoint returns HTTP 503 with a retry time. That distinction lets the interface explain whether a visitor's allowance or the site's shared allowance is exhausted.

## The counter has two parts

Each bucket uses a fixed window based on Unix time. The bucket and window identify the KV key. When the window changes, new requests use a different key; old entries expire through KV's TTL.

An in-memory counter increments before the first asynchronous operation. That prevents two requests in the same isolate from both reading the same local count before either consumes it. KV then provides persistence across requests that reach other isolates.

The local counter is useful, but it does not coordinate all of Cloudflare's isolates. It is also cleared when an isolate restarts. Its correctness boundary is one running isolate, not the entire deployment.

A turn consumes its allowance before the upstream call. Failed upstream calls are therefore still attempts against the allowance. That is conservative for abuse control, although it means a failed answer can cost the visitor a question.

## Where KV stops being a quota

Workers KV is eventually consistent. Separate locations can read stale counts, and concurrent writes can overwrite one another. Cloudflare also documents a limit of one write per second to the same key. A shared daily key can encounter that write limit even when the inference service itself has capacity. See [Cloudflare's KV write guidance](https://developers.cloudflare.com/kv/api/write-key-value-pairs/).

Those properties prevent this implementation from promising exactly 300 admitted turns across the whole deployment. The in-memory counter narrows one race; it does not make distributed read-modify-write atomic. There is no measured, fixed multiplier that justifies saying over-admission is always small.

When the requirement is an exact shared quota, use a coordination mechanism that supports the needed atomic decision. Cloudflare recommends [Durable Objects when stronger consistency is required](https://developers.cloudflare.com/kv/concepts/how-kv-works/). That would be a different implementation, not a property this counter already has.

## Missing storage is a distinct failure mode

If the KV binding is absent, the current limiter continues with its in-isolate counter. That supports local development, but in production it would remove durable coordination and allow fresh allowances as isolates restart or multiply.

A low per-call cost does not make unlimited aggregate traffic bounded. The production choice needs to be explicit: refuse live requests when the required storage is missing, or accept that the limiter is best-effort and enforce a separate spending boundary.

The article can state that tradeoff honestly without pretending the stricter policy is already implemented.

## Bound the bill separately

A cost estimate starts with admitted calls, input and output tokens, model prices, and any additional attempts. Every term needs a stated assumption. Multiplying a soft request limit by a cheap call does not turn either into a hard global cap.

For a public demo, I want both useful application controls and an independent provider-side spending limit where one is available. I also want a clear way to disable live inference. These are requirements for a stronger budget contract, not claims about controls that this repository has already proven.

The [Flagship case study](/work/flagship) explains the interface and agent architecture. The lesson here is narrower: describe a limiter by the coordination it actually provides. Call a target a target, and reserve “guarantee” for a bound the implementation can enforce.
