In the [data structures field guide](/blog/data-structures-typescript-python), graphs got a row in the table and a promise of their own post. This is that post, and it starts with the thing that makes graphs different from every other row: **you almost never instantiate one.** There is no `Graph` class to memorize. A graph is a hash map from node to neighbor list, built in four lines, and everything interesting lives in how you walk it.

```python
from collections import defaultdict

graph: dict[int, list[int]] = defaultdict(list)
for u, v in edges:
    graph[u].append(v)
    graph[v].append(u)   # undirected — drop this line for directed
```

```ts
const graph = new Map<number, number[]>();
for (const [u, v] of edges) {
  if (!graph.has(u)) graph.set(u, []);
  if (!graph.has(v)) graph.set(v, []);
  graph.get(u)!.push(v);
  graph.get(v)!.push(u); // undirected
}
```

That is the adjacency list, and it is the right representation for nearly everything — O(V + E) space, O(1) edge insertion, neighbors iterable in degree time. The adjacency *matrix* earns its O(V²) memory only when the graph is dense or you need O(1) "is there an edge between u and v?" queries.

From there, two booleans select the algorithm:

| Question | Unweighted | Weighted |
| --- | --- | --- |
| Shortest path | BFS | Dijkstra |
| Reachability / components | BFS or DFS | BFS or DFS |
| Cycle detection, topological order | DFS | DFS |
| Negative edge weights | — | Bellman-Ford (rare) |

Three algorithms cover the table. Each is the previous one with the queue swapped out.

## BFS: the queue visits in distance order

BFS's bet: process nodes in the order they were discovered, and you process them in order of distance from the start. The invariant is worth saying out loud — *the queue only ever holds nodes at distance d and d+1, in that order* — because it is the entire proof that the first time you reach a node is the shortest way to reach it. That only holds when every edge costs the same, which is why BFS is the unweighted column of the table.

```python
from collections import deque

def bfs(graph: dict[int, list[int]], start: int) -> dict[int, int]:
    dist = {start: 0}
    queue = deque([start])
    while queue:
        node = queue.popleft()
        for neighbor in graph[node]:
            if neighbor not in dist:
                dist[neighbor] = dist[node] + 1
                queue.append(neighbor)
    return dist
```

The [queue trap](/blog/data-structures-typescript-python) from the field guide shows up here on schedule: Python's `deque.popleft()` is O(1), but the literal TypeScript translation uses `Array.shift()` and goes quietly quadratic on large graphs. The dependency-free fix is a read-index — never remove anything, just walk a pointer forward:

```ts
function bfs(graph: Map<number, number[]>, start: number): Map<number, number> {
  const dist = new Map([[start, 0]]);
  const queue = [start];
  let head = 0;                       // read-index: O(1) "dequeue", no shift()
  while (head < queue.length) {
    const node = queue[head++];
    for (const neighbor of graph.get(node) ?? []) {
      if (!dist.has(neighbor)) {
        dist.set(neighbor, dist.get(node)! + 1);
        queue.push(neighbor);
      }
    }
  }
  return dist;
}
```

One detail that separates working BFS from subtly-broken BFS: mark nodes visited **when you enqueue them**, not when you dequeue them. Mark-on-dequeue lets the same node enter the queue many times through different neighbors, and on a dense graph that turns O(V + E) into something much worse — without changing the answers, which is exactly the kind of bug a contest judge punishes with "time limit exceeded" and production punishes with a pager.

## DFS: the stack answers structure questions

Swap the queue for a stack and you get DFS. The distance-order guarantee is gone; what you get instead is **completion order** — a node finishes only after everything reachable from it has finished — and that is the property behind every structural question: does this graph have a cycle? What order do these dependencies resolve in? How many islands are there?

The recursive version is the one everyone writes, because the call stack *is* the stack:

```python
def dfs(graph: dict[int, list[int]], node: int, visited: set[int]) -> None:
    visited.add(node)
    for neighbor in graph[node]:
        if neighbor not in visited:
            dfs(graph, neighbor, visited)
```

And here is the production gotcha neither language warns you about: **recursion depth is an input-dependent resource.** Python's default limit is 1,000 frames — a path graph with 10,000 nodes crashes correct code with `RecursionError`. JavaScript engines die the same way around a few thousand frames, just with a less helpful `RangeError`. `sys.setrecursionlimit` is a band-aid; the real fix is the iterative version with an explicit stack, which is the same algorithm with the resource limit moved from the runtime to the heap:

```ts
function dfs(graph: Map<number, number[]>, start: number): Set<number> {
  const visited = new Set([start]);
  const stack = [start];
  while (stack.length) {
    const node = stack.pop()!;
    for (const neighbor of graph.get(node) ?? []) {
      if (!visited.has(neighbor)) {
        visited.add(neighbor);
        stack.push(neighbor);
      }
    }
  }
  return visited;
}
```

Run that from every unvisited node and count the runs: that is connected components. Track nodes currently *on* the recursion path (not just visited) and a revisit means a cycle. Record the order nodes finish and reverse it: topological sort. All the structure questions are DFS plus one extra piece of bookkeeping.

## Dijkstra: BFS where the queue becomes a heap

Make the edges weighted and BFS's invariant breaks — the first time you reach a node is no longer the cheapest. The repair is to always expand the *cheapest known frontier node* instead of the oldest, which means the queue becomes a min-heap, which means this is the [heap gap](/blog/data-structures-typescript-python) from the field guide all over again: Python has `heapq`, TypeScript has nothing.

```python
import heapq

def dijkstra(graph: dict[int, list[tuple[int, int]]], start: int) -> dict[int, int]:
    dist = {start: 0}
    heap = [(0, start)]                    # (cost, node)

    while heap:
        cost, node = heapq.heappop(heap)
        if cost > dist.get(node, float("inf")):
            continue                       # stale entry — skip
        for neighbor, weight in graph[node]:
            new_cost = cost + weight
            if new_cost < dist.get(neighbor, float("inf")):
                dist[neighbor] = new_cost
                heapq.heappush(heap, (new_cost, neighbor))
    return dist
```

The subtle line is the stale-entry skip. `heapq` has no decrease-key operation, so when a cheaper route to a node is found, the old, more expensive heap entry is not removed — it is left to rot and discarded when it surfaces. That "lazy deletion" is the standard trick, it keeps the complexity at O((V + E) log V), and forgetting the skip gives you an algorithm that is correct but re-expands nodes for no reason.

In TypeScript, you face the same choice as in the field guide: for interview-sized inputs, a sorted array wearing a heap's interface is fine *if you say the cost out loud*; for production, a priority-queue dependency is one of the few data-structure imports that genuinely earns its place in `package.json`.

## The recognition table

| You hear | You reach for |
| --- | --- |
| "Fewest hops / moves / steps" | BFS |
| "Can A reach B?" | BFS or DFS, either |
| "Cheapest route", weights ≥ 0 | Dijkstra |
| "Valid build/course order" | DFS topological sort |
| "How many groups/islands?" | DFS components (or Union-Find) |
| "Is there a circular dependency?" | DFS with on-path tracking |

The deeper habit is noticing that a graph problem rarely announces itself as one. Package dependencies, currency conversion chains, social follows, state machines, spreadsheet cell references — none of these say "graph" in the ticket. The skill the contest table drills is hearing *nodes and edges* in a problem that was stated in nouns and verbs, and then asking the only two questions that matter: are the edges weighted, and what do I actually need — a distance, an order, or a yes/no. Two booleans and a question. The algorithm picks itself.
